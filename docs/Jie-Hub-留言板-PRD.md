# Jie Hub 全站留言板产品需求文档（PRD）

| 项目 | 内容 |
| --- | --- |
| 产品名称 | Jie Hub 全站留言板 |
| 文档版本 | V1.2 |
| 需求优先级 | P0：必须实现；P1：后续迭代 |
| 目标版本 | MVP（基础版） |
| 使用终端 | PC、移动端 Web |

## 1. 项目背景与目标

Jie Hub 是展示 Web 案例与个人作品的网站。新增独立的「留言板」页面，供访客表达建议、提问和交流，由站长统一审核与回复。

目标：

1. 访客无需注册即可提交留言。
2. 访客能查看已公开的留言及二级回复，并参与交流。
3. 站长能审核、回复和管理留言。
4. 具备基础的内容安全与防刷能力。

本期仅实现**全站统一留言板**，不关联具体作品。

## 2. 用户角色与权限

| 角色 | 查看已公开留言 | 提交留言 | 回复留言 | 审核/隐藏/删除 |
| --- | --- | --- | --- | --- |
| 游客 | 是 | 是 | 是（二级回复） | 否 |
| 管理员（站长） | 是 | 是 | 是 | 是 |

游客不要求账号登录；管理员需通过受保护的管理入口验证身份。匿名用户不具备编辑或删除已提交留言的能力。

## 3. 本期功能范围

### 3.1 前台：留言板页面（P0）

**入口与结构**

- 网站导航提供「留言板」入口。
- 页面包含标题/说明、留言输入区、公开留言列表、分页区域。
- PC 与移动端均可正常浏览、输入和提交。

**提交留言**

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 昵称 | 是 | 2–20 个字符，去除首尾空格 |
| 留言内容 | 是 | 5–500 个字符，去除首尾空格 |

- 表单显示剩余可输入字数、必填提示与校验错误。
- 点击「提交留言」后，按钮进入提交中状态，避免重复点击。
- 提交成功提示「留言已提交，审核通过后将公开展示」。
- 提交失败保留已输入内容，并展示可理解的错误提示。
- 默认不收集邮箱、手机号、真实姓名等个人信息。
- 昵称是显示名称，不能用于证明访客身份。

**两层楼中楼回复**

- 一级为主留言；二级为主留言下的回复，最多展示两层，不产生第三级。
- 游客可回复一级留言，也可点击某条二级回复的「回复」按钮。
- 回复二级回复时仍创建在同一一级留言下的二级回复，显示「回复 @目标昵称」，不继续嵌套。
- 回复表单沿用昵称、内容的必填校验规则；提交后进入待审核，审核通过才展示。
- 游客只能回复已公开的留言；昵称可能重复，系统需根据回复记录确定被回复对象，而不是仅依赖昵称。
- 一级留言被隐藏或删除时，所属二级回复一并从前台隐藏。

**留言列表**

- 只展示审核通过且未被隐藏、未删除的留言。
- 每条一级留言展示：昵称、内容、发布时间、二级回复列表及回复入口。
- 每条二级回复展示：昵称、内容、发布时间，以及被回复的昵称（若回复的是其他二级回复）；管理员回复标识「站长」。
- 一级留言默认按发布时间倒序排列；同一一级留言下的二级回复按发布时间正序排列。
- 每页展示 10 条一级留言，支持翻页；二级回复按所属一级留言加载，数量较多时支持「展开更多回复」。没有留言时展示友好的空状态。
- 文本换行可正常显示；留言以纯文本展示，不执行 HTML、脚本或富文本代码。
- 列表刷新后仍按相同排序规则展示，不因审核中的留言产生空白项。

### 3.2 后台：留言管理（P0）

**管理列表**

- 管理员查看全部留言，包括待审核、已通过、已拒绝及已隐藏的记录。
- 展示昵称、内容摘要、提交时间、审核状态、留言层级及所属一级留言。
- 支持按状态筛选，按昵称或内容关键词搜索，以及分页查询。

**审核操作**

- 新留言默认进入「待审核」，前台不可见。
- 管理员可执行「通过」或「拒绝」。
- 已通过留言可「隐藏」，隐藏后前台立即不可见；可再次恢复展示。
- 支持删除留言，删除需二次确认；删除后前台不可见。

**回复管理**

- 管理员可以对已公开的一级留言或二级回复进行回复，内容长度为 5–500 个字符。
- 站长回复与游客回复共用二级结构，前台明确标识「站长」，不限制每条一级留言只有一条站长回复。
- 管理员可以审核、隐藏或删除任意二级回复；可以编辑或删除自己发布的站长回复。
- 一级留言被隐藏或删除时，其所有二级回复同步不在前台展示。

### 3.3 基础防护（P0）

- 限制昵称和留言长度，服务端必须再次校验，不仅依赖前端校验。
- 限制提交频率：同一访问来源默认每 60 秒最多提交 1 次；触发限制时提示稍后重试。
- 对重复内容和异常高频请求进行拦截或记录，防止机器刷屏。
- 全部用户输入按纯文本处理，防止 XSS 等注入风险。
- 访客不能调用管理员操作；管理员接口必须进行身份与权限校验。
- 不在公开页面或接口返回内部风控标识、访客 IP 等信息。
- 管理员可以拒绝广告、辱骂、违法违规或泄露隐私的内容。

## 4. 业务流程

1. 游客进入「留言板」，查看已公开留言。
2. 游客填写昵称与留言，点击提交。
3. 系统校验内容及频率：不通过则提示错误；通过则保存为「待审核」。
4. 访客可对已公开的一级留言或二级回复发起回复，系统统一记录为二级回复并送审。
5. 管理员在后台分别审核一级留言和二级回复，选择通过或拒绝。
6. 审核通过后才在对应位置展示；拒绝后不展示。
7. 管理员可回复、隐藏或删除已公开的留言及回复。

## 5. 留言状态规则

| 状态 | 含义 | 前台可见 | 后台可执行操作 |
| --- | --- | --- | --- |
| 待审核 | 刚提交，尚未处理 | 否 | 通过、拒绝、删除 |
| 已通过 | 已审核并公开，且其所属一级留言也已公开 | 是 | 回复、隐藏、删除 |
| 已拒绝 | 审核不通过 | 否 | 重新通过、删除 |
| 已隐藏 | 曾公开，管理员主动下架 | 否 | 恢复展示、删除 |
| 已删除 | 已移除 | 否 | 不在常规列表中操作 |

删除方式属于实现层决策，但必须满足前台不再展示；后台操作应能追踪操作时间及执行者，以便排查误操作。

## 6. 页面交互与状态

| 场景 | 预期行为 |
| --- | --- |
| 首次进入 | 加载第一页已公开留言 |
| 正在加载 | 显示加载状态，避免重复请求 |
| 无公开留言 | 显示「还没有留言，欢迎留下第一条」 |
| 加载失败 | 显示失败提示和「重试」入口 |
| 表单信息不合法 | 在对应字段附近说明原因，不提交 |
| 重复点击提交 | 首次请求处理中禁用提交按钮 |
| 提交成功 | 提示需审核；不立即插入公开列表 |
| 提交过快 | 提示提交频繁，稍后重试 |
| 管理员审核通过 | 下次获取公开列表时可看到新留言 |
| 管理员隐藏留言 | 后续公开列表与详情请求不再返回该留言 |
| 回复一级留言 | 填写回复并提交审核；通过后显示在该一级留言的第二层 |
| 回复二级回复 | 输入区提示回复对象；审核通过后仍显示在第二层，并标注被回复昵称 |
| 回复数量较多 | 展示部分回复并提供「展开更多回复」，不影响一级留言分页 |

## 7. 数据需求（业务字段）

留言记录至少包含：留言 ID、昵称、内容、提交时间、审核状态、审核时间、审核人、隐藏状态、留言层级、所属一级留言 ID、被回复留言 ID、是否站长回复。

- 一级留言没有所属一级留言 ID，层级为 1。
- 二级回复关联所属一级留言 ID，层级为 2；若回复的是另一条二级回复，另记录被回复留言 ID。
- 系统必须保证任何回复均不会生成第三级结构。若被回复内容已隐藏或删除，不应继续对其发起回复。

为风控可在服务端保留必要的访问来源标识，但不对访客公开；相关数据应限制访问权限与保留期限。

本期不需要作品 ID、用户账号 ID、点赞数或第三级及以上回复关系。

### 7.1 数据表设计约定

- 以 **MySQL 8.x** 为字段类型参考，采用 `snake_case` 命名；本节为产品数据设计，不包含建表 SQL。
- 业务主键使用 `BIGINT`；时间使用 `DATETIME`，统一约定存储时区。
- 本期设计两张业务表：`guestbook_comment`（留言与二级回复）、`guestbook_audit_log`（审核及管理操作日志）。
- 不需要单独建立一级留言表和二级回复表，也不需要创建作品评论表。

### 7.2 留言表 `guestbook_comment`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | 是 | 主键，留言或回复唯一 ID |
| `root_id` | BIGINT | 否 | 所属一级留言 ID；一级留言为 NULL，二级回复必填 |
| `reply_to_id` | BIGINT | 否 | 被回复的记录 ID；一级留言为 NULL，二级回复必填，可指向一级或同一楼中的二级回复 |
| `level` | TINYINT | 是 | 层级，仅允许 1 或 2 |
| `nickname` | VARCHAR(20) | 是 | 发布人显示昵称 |
| `content` | VARCHAR(500) | 是 | 纯文本内容 |
| `author_type` | VARCHAR(10) | 是 | `visitor` 游客、`admin` 站长；不依赖昵称判定身份 |
| `admin_id` | BIGINT | 否 | 站长发表时关联后台管理员 ID；游客为 NULL |
| `status` | VARCHAR(20) | 是 | `pending` 待审核、`approved` 已通过、`rejected` 已拒绝、`hidden` 已隐藏 |
| `created_at` | DATETIME | 是 | 提交时间 |
| `updated_at` | DATETIME | 是 | 最后修改时间 |
| `reviewed_at` | DATETIME | 否 | 最近一次审核时间 |
| `reviewed_by` | BIGINT | 否 | 最近一次审核管理员 ID |
| `deleted_at` | DATETIME | 否 | 软删除时间；非 NULL 时视为已删除 |
| `source_hash` | VARCHAR(128) | 否 | 服务端生成的访问来源摘要，仅用于频率限制与风控，不对外公开 |

**字段与关联约束**

1. `level = 1`：`root_id`、`reply_to_id` 均为 NULL。
2. `level = 2`：`root_id` 指向有效一级留言；`reply_to_id` 指向该一级留言或同一 `root_id` 下的二级回复。
3. 二级回复不得充当新的 `root_id`；禁止跨楼回复关联，避免形成第三级嵌套。
4. `author_type = admin` 时 `admin_id` 必填；游客无需用户 ID。
5. 公开查询仅返回 `status = approved` 且 `deleted_at IS NULL` 的记录；二级回复还要求其一级留言处于同样的公开状态。
6. 管理员隐藏或删除一级留言时，可保留其二级回复记录用于管理审计，但前台必须整体不可见。
7. 被回复内容在提交时必须存在且可见；对已隐藏、删除或未审核的内容禁止继续回复。

**推荐索引（逻辑设计）**

| 索引名称 | 字段 | 用途 |
| --- | --- | --- |
| `idx_root_status_time` | `root_id`, `status`, `deleted_at`, `created_at`, `id` | 查询一级留言及同楼二级回复 |
| `idx_status_time` | `status`, `deleted_at`, `created_at`, `id` | 公开列表和后台按状态筛选 |
| `idx_source_time` | `source_hash`, `created_at` | 基础防刷与频率检查 |

一级留言通过 `root_id IS NULL` 分页；二级回复按 `root_id` 分批加载。稳定排序应在时间相同时以 `id` 作为次排序字段。

### 7.3 审核操作日志表 `guestbook_audit_log`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | 是 | 主键 |
| `comment_id` | BIGINT | 是 | 被操作的留言或回复 ID |
| `operator_id` | BIGINT | 是 | 管理员 ID |
| `action` | VARCHAR(20) | 是 | `approve`、`reject`、`hide`、`restore`、`delete` |
| `before_status` | VARCHAR(20) | 否 | 操作前状态 |
| `after_status` | VARCHAR(20) | 否 | 操作后状态 |
| `created_at` | DATETIME | 是 | 操作时间 |
| `remark` | VARCHAR(255) | 否 | 审核或管理备注，仅后台查看 |

- 推荐索引：`(comment_id, created_at)`、`(operator_id, created_at)`。
- 审核或管理状态变更应与日志写入保持一致，防止记录状态与操作历史不符。
- 删除留言不应导致其既有操作日志丢失；日志仅授权管理员查看。

### 7.4 数据展示示例

| id | root_id | reply_to_id | level | nickname | 内容示例 |
| --- | --- | --- | --- | --- | --- |
| 100 | NULL | NULL | 1 | 小明 | 网站做得不错 |
| 101 | 100 | 100 | 2 | 小李 | 谢谢分享 |
| 102 | 100 | 101 | 2 | 站长 | 回复 @小李：欢迎交流 |

以上 102 号记录虽然回复了 101 号二级回复，但依然归属 100 号一级留言，前台展示层级仍为 2。

## 8. 非功能性要求

- **兼容性**：支持主流现代桌面与移动浏览器；窄屏不横向溢出。
- **可用性**：按钮、输入框和错误提示清晰；支持键盘操作和可见焦点。
- **性能**：公开留言必须分页获取，不一次性加载全部记录。
- **安全性**：服务端校验、权限鉴权、防刷、文本安全输出为必备要求。
- **隐私**：仅收集完成留言功能所需的信息；公开页不泄露访问来源数据。
- **异常处理**：网络失败时不丢失游客当前输入；管理操作失败时给予明确反馈。

## 9. MVP 验收标准

- [ ] 从网站导航可以进入留言板；PC、移动端显示正常。
- [ ] 游客能查看公开的一级留言和二级回复，并正常分页。
- [ ] 游客能回复一级留言或二级回复；回复二级回复仍显示在第二层，正确标注回复对象。
- [ ] 任何操作都不会产生第三级评论；一级留言隐藏或删除后其回复全部不可见。
- [ ] 昵称或内容为空、过短或过长时不能提交。
- [ ] 合法留言提交后进入待审核，前台不会立即公开。
- [ ] 管理员可筛选、搜索、分页管理留言。
- [ ] 管理员可以通过、拒绝、隐藏、恢复和删除留言。
- [ ] 通过审核的留言显示在前台；拒绝/隐藏/删除的留言不显示。
- [ ] 管理员可审核、隐藏和删除二级回复；可发布、编辑、删除自己的站长回复。
- [ ] 连续快速提交会受到限制；重复点击不会创建重复留言。
- [ ] 输入包含 HTML 或脚本字符串时只按普通文本显示，不被执行。
- [ ] 未登录管理员身份的请求不能进行审核或管理操作。
- [ ] 网络异常、空列表、提交成功与提交失败均有明确反馈。

## 10. 暂不纳入 V1.2

- 用户注册、登录和个人主页。
- 第三级及以上嵌套回复、独立的 @用户通知功能。
- 点赞、表情、图片或附件上传。
- Markdown、富文本编辑器。
- 邮件或站内消息通知。
- 按单独作品划分评论区。
- 敏感词词库自动审核、复杂验证码或 AI 内容审核（后续可按垃圾留言情况评估）。

## 11. 待确认事项

本版按以下默认产品决策推进：游客匿名发布、游客与站长均可参与两层楼中楼回复、全部内容人工审核后公开、一级留言每页 10 条、纯文本内容。回复标注「@昵称」仅用于显示回复目标，不产生账户提醒。如未来增加作品评论或更深层级讨论，应单独增加需求版本。
